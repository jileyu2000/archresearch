# ArchResearch V2.1 Implementation Plan

## Goal

Build the approved local-first architecture research agent: a Chrome MV3 extension, a local FastAPI research executor, and a visual research board. The runtime must use live web research without a platform case library or global vector index.

## Success Criteria

- A user can create a workspace, add text/image/PDF/URL inputs, and start a persisted research run.
- The run follows a deterministic state machine, streams progress, and preserves partial results.
- OpenAI and TinEye have real adapters plus deterministic mock implementations.
- The Chrome extension pairs locally, requests/revokes optional host permissions, and executes only the approved browser action DSL.
- Results expose evidence tiers, saved/rejected actions, comparison, exports, and optional style extraction.
- API, board, and extension tests pass; lint/type checks/builds pass; README documents a local demo.

**Assumptions and scope**

**Observed task set: 8–10 tasks total**

1. At least three architectural-research tasks based on a real spatial/design conflict; at least one uses a participant-provided project brief PDF.
2. At least two drawing-inspiration tasks with a clearly named drawing type or visual direction.
3. At least three downstream tasks covering understanding result states and case summaries, reopening a history record, and saving then retrieving a personal collection item.
4. Distribute tasks so every participant completes one core research task and one evidence/continuity task; rotate the PDF and visual paths across the cohort.

**Observation record per task**

- Outcome: completed without help / completed with help / failed.
- Time: start-to-submit, wait-to-terminal-result, and time-to-find the first useful answer or image.
- Choice quality: correct mode, research depth, optional material use and question specificity.
- Trust and comprehension: whether the participant distinguishes completed research, initial evidence, formal project cases, preview leads and visual-inspiration-only material.
- Navigation and continuity: whether the participant can understand the result structure, return, reopen history and retrieve a saved collection without prompting.
- Failure behavior: unclear recovery, duplicate submission, retry expectation, lost input, blocked action or misleading status.

**Severity and decision gate**

- P0: data loss, unsafe action, credential/privacy exposure or irreversible corruption.
- P1: cannot finish a core task, materially misleading evidence/completion claim or repeated wrong-mode submission.
- P2: task finishes only with help, major navigation confusion or repeated comprehension failure.
- P3: isolated wording, density or polish issue that does not block the task.
- Propose one bounded repair phase only for any P0/P1 finding, or for the same P2 pattern observed in at least two participants. Record one-off P2/P3 findings without implementation.
- M121 becomes complete only after all 2–3 participants and 8–10 tasks are documented with a severity/frequency matrix. If no repair threshold is met, the next proposed phase is M122 characterization; if a threshold is met, define one behavior-first repair milestone before any code change.

**Acceptance**

- Participant/task coverage and every observation field are complete and de-identified.
- A ranked finding matrix links each issue to concrete tasks and participant frequency; no conclusion relies on one anecdote alone unless it is P0/P1.
- Final state is 3 projects / current Run count / active 0; all participant-created Runs are attempt 0 and no sealed Run was retried.

## Decisions

- React + Vite instead of Next.js: the board is a local SPA with no SSR requirement.
- FastAPI + SQLAlchemy + SQLite; no PostgreSQL, Redis, S3, Celery, Docker, Qdrant, LangGraph, or multi-agent runtime.
- Direct OpenAI Responses API with strict schemas; custom local trace to control sensitive data.
- Research and visual classification default to `gpt-5.6-sol` with `medium` reasoning; both model names remain environment-overridable.
- The `suoxie` relay key is accepted only through hidden PowerShell input, tested before commit, and stored in Windows Credential Manager; provider JSON contains no secret.
- Project automation defaults to PowerShell 7 (`pwsh`); Windows PowerShell 5.1 is used only for explicit compatibility checks.
- All browser commands are enumerated JSON messages; no arbitrary selectors, JavaScript, credentials, social actions, or general form submission.
- Temporary candidates expire after 7 days; run metadata/trace after 30 days; explicit saves persist until deletion.
- Research depth is a semantic contract: problem decomposition, per-subquestion source/project/drawing coverage and analysis/evidence obligations. Query/page/time values are bounded execution ceilings, not the user-facing definition of depth.
- Quick, Balanced and Deep all owe a complete answer across their planned subquestions. Depth changes enrichment and analysis rigor, never permission to deliver a knowingly incomplete answer as complete. External blockers remain explicit and resumable.
- Deterministic replay fixtures remain the zero-cost development and regression path. Final portfolio demonstrations must be three real Quick/Balanced/Deep research runs and result-page screenshots; live Firecrawl execution retains a configurable reserve until those acceptance runs.
- Xiaohongshu support uses only the user's visible, signed-in Chrome pages after explicit one-time permission. The system never asks for or stores a password, reads cookies/local storage/private messages, bypasses verification, or performs social actions; the user can revoke access from the extension at any time.
- Source priority follows research intent: authoritative architecture/project sources establish case facts and completion; Xiaohongshu is the sole visual-inspiration source for drawing style, massing and diagram language and cannot alone prove a complete project case.
- Pinterest was removed from the current product in M94. It is not an accepted source value or Board option, and unexpected Pinterest/`pin.it` Provider results are discarded before persistence.

- 目标：让 `scripts/start.ps1` / `stop.ps1` 在这台机器上可靠工作，不再出现"启动完立刻被自己杀掉"的状态；范围只限 `scripts/`，不触碰产品代码、schema、迁移、durable data 或任何 Run。
- 根因：`dev-common.ps1` 的两个探测原语都走 CIM——`Get-TcpListeningProcessIds` 用 `Get-NetTCPConnection`，`Get-ProcessCommandLine` 用 `Get-CimInstance Win32_Process`。本机 MSIX 版 pwsh 7.6.4 加载 `Microsoft.Management.Infrastructure.Native.Unmanaged.DLL` 返回 `E_ACCESSDENIED`，`start.ps1:94-101` 的归属校验因此抛错，catch 分支 `Stop-Process -Force` 把刚拉起的 API 与 Board 一起清掉。
- 改动：两处原语改为无 WMI 实现。监听进程改用 `netstat -ano`，按环回本地端点加"未连接"的对端地址（`0.0.0.0:0` / `[::]:0` / `*:*`）判定，不依赖本地化的状态词；命令行改用 `ntdll!NtQueryInformationProcess` 读 PEB 的 `RTL_USER_PROCESS_PARAMETERS.CommandLine`，按需 `Add-Type` 一次。`Test-CommandLineReferencesWorkspace` 的工作区归属语义、函数签名与全部调用点均未改变。
- 环境侧修复：pnpm 之前由 Codex 运行时提供，本机并未安装，`Resolve-WorkspaceRuntime` 因此直接抛错。已按根 `package.json` 的 `packageManager` 安装 `pnpm@11.7.0` 至 `%APPDATA%\npm`。
- 验收：先复现红灯（`process-lifecycle.tests.ps1` 因 CIM 类型初始化异常整体失败），补入无 WMI 断言后实现，再跑真实生命周期——`Get-WorkspaceListeningProcessIds` 正确识别 vite(node) 与 uvicorn(python) 两个监听进程，`start.ps1` 写出 state、重复调用走复用分支、`stop.ps1` 清理干净、再次 `start.ps1` 恢复服务。
