## Approved Product Decisions

- Runtime: local Windows/Chrome single-user application.
- Surfaces: Chrome MV3 extension + local board + local FastAPI executor.
- Storage: SQLite and local files only.
- Search: OpenAI web search for text/image discovery; Chrome for page inspection; TinEye for reverse image lookup.
- Result delivery: verified, partial, and visual-lead tiers; private full export and rights-filtered share export.
- No platform case library, global index, or cross-workspace retrieval.

## Frontend Direction

- Subject: an architectural evidence desk, not a chat application.
- Layout: compact top bar, one research composer and a flat drawing grid. Workspaces use a selector; evidence and Trace use contextual drawers; compare actions appear only after selection.
- Palette: vellum `#F3F5F2`, graphite `#171B19`, blueprint `#315CF4`, signal red `#E4583E`, evidence green `#2D846B`, fog `#DDE3DF`.
- Type: system Chinese sans for readability, condensed/mono utility labels for drawing metadata.
- Default disclosure: cards show the drawing, project, type, evidence tier and one useful sentence; provenance, claims, boundaries, notes, StyleProfile, exports and Trace stay one explicit action away.
- Avoid permanent side rails, repeated filter buttons, generic rounded SaaS cards, decorative gradients, and chat-first layout.

## Implemented Boundaries

- Browser pairing rotates a one-time code to a persistent token; only its SHA-256 digest is stored by the API.
- Browser commands are enumerated and payload-strict. Generic `safe_click` is a no-op on untrusted pages.
- Candidate inspection sends at most three cropped regions per page to the visual classifier; full pages and image data are excluded from Trace.
- API DNS resolution rejects failed, private, reserved, and IPv4-mapped private A/AAAA results before navigation; the extension rechecks final URLs.
- Saved-reference snapshots survive temporary candidate cleanup. Startup cleanup removes expired candidates, source metadata, queries, and Trace, then resumes active runs.
- Board and API currently run as user-session background processes, not Windows services. A reboot or host process cleanup can leave the saved launcher state behind while ports 5173/8000 are no longer listening; `scripts/start.ps1` safely recreates both listeners and rewrites the state file.

## M15 Research-depth correction

- M14 made the result understandable but did not deepen the research itself: one ranked `inference` per asset still produces a gallery with short captions rather than a decomposed architectural argument.
- The required unit of presentation is no longer a single image card. It is `subquestion → project dossier → multiple supporting assets`, with each dossier explaining project conditions, spatial mechanism, visible evidence, transferable operation, mismatch/boundary and provenance.
- This remains task-scoped real-time research. Subquestions, project groupings and temporary assets belong to one `ResearchRun`; they do not form a platform case library or cross-workspace index.
- Depth modes must change evidence obligations rather than only time limits: Quick should cover at least 3 subquestions / 2 projects / 6 assets, Balanced 4 / 4 / 12, and Deep 5–6 / 6 / 18 when the live web supplies usable evidence. Partial delivery remains valid when those targets cannot be met.
- A previously seen asset can legitimately advance a new subquestion. Duplicate persistence now unions task-scoped subquestion associations; only a batch that adds neither a new asset nor a new association counts as empty.
- Browser inspection considers up to six candidate media regions per page, while run-level capture, preview-byte and page-attempt budgets are reserved and committed to SQLite before more work proceeds. Crop dimensions, public-URL checks and temporary storage rules remain bounded across restarts.
- `project_context` is useful dossier context but does not become a formal fact merely because the model emitted it. Persistence creates evidence claims only from exact entries in `facts`; context is source-supported only when the provider repeats the exact claim there. `design_mechanism` and transfer steps remain explicitly interpretive analysis.
- The durable plan records 3 / 4 / 6 subquestions for Quick / Balanced / Deep and uses their stable IDs in query attempts. The stored token means the user should not pair for every run; the authenticated heartbeat keeps that already paired socket available between browser actions. Temporary page permissions remain scoped to the active research session and are still revoked at terminal states.
- Real Chrome acceptance confirms the distinction: after rebuilding and reloading once, all ten connection samples over 45 seconds remained authenticated. Normal research runs can now reuse the stored token and live bridge without re-pairing; only replacing/reloading extension storage or deleting the local pairing token should require a new code.

## M26 Quick-path performance and timeout isolation

- The repeated `APITimeoutError` is emitted by the OpenAI-compatible relay call, not by Firecrawl or the local browser. In the latest live Quick run, planning took about 8.5 seconds, Firecrawl Search returned four sources in about 1.8 seconds, and the first model search then occupied roughly 121 seconds before timing out. The remaining model calls were skipped to protect the 240-second deadline.
- Increasing Quick's total duration would hide rather than fix the bottleneck. The performance target is to cap optional model search enrichment to a smaller share of each mode, preserve independent Firecrawl/Chrome progress, and avoid repeated slow calls once the relay demonstrates timeout behavior during the same run.
- Current provider settings already match the low-latency OpenAI search controls: Responses `web_search`, `search_context_size: low`, and `reasoning.effort: low`. The avoidable delay is local retry policy: a 60-second SDK timeout with one automatic retry produces the observed 120-second critical path.
- The narrow M26 correction is a 30-second no-retry provider client plus a run-scoped timeout circuit. After one model-search timeout, later query batches continue through Firecrawl and Chrome but do not repeat the same slow model call. Planning still has deterministic fallback, and a new research run resets the circuit.
- Live comparison confirms the circuit behavior: the first relay search ended at 30 seconds, then all later model checkpoints recorded `previous_timeout` while Firecrawl continued across the remaining subquestions. The total run improved by about 51 seconds (roughly 26%) despite inspecting more public pages than the old run.
- The comparison was started through the local API to keep the question identical, so it did not invoke the Board's user-gesture permission request. Its `BrowserCommandError` events do not show a broken extension; they show that direct API starts intentionally lack temporary site access. A normal Board-started run is still required to exercise precise Chrome crops.
- Firecrawl's official v2 API accepts an explicit millisecond timeout. The final 20-second bound is sent to both `/search` and `/scrape` and also enforced by the local HTTP client, preventing one slow PDF/page from consuming 30 seconds while preserving later-source progress.
